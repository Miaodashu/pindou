# 图片转换架构

## 目标

图片转换不是简单缩小图片，而是把原图变成可制作、可核对、可继续编辑的拼豆图纸。系统需要同时保留主体轮廓、限制实际用色数量、输出确定的色号，并向用户暴露颜色匹配的不确定性。

## 处理流水线

1. 浏览器解码图片，按“自由裁切”“裁剪铺满”或“完整放入”映射到目标拼豆网格。
2. 将 RGBA 像素传给 Web Worker；Worker 按需加载 OpenCV.js/WASM。
3. OpenCV 使用面积插值缩放，并通过灰度图与 Canny 生成边缘权重；加载失败时使用 Canvas 与亮度梯度降级。
4. 可选去背先对目标图执行边缘连通洪水填充，只清除接近角点主色且与边缘相连的区域；被轮廓包围的同色内部细节继续保留。
5. Worker 把像素转换到 CIE Lab，在完整色卡中用 CIEDE2000 计算感知色差。
6. “最接近原图”逐格使用完整色卡；“均衡推荐”和“最少颜色”以加权贪心方式选择不超过上限的真实色号子集，边缘像素获得更高权重。
7. 每个网格只记录色卡索引；界面展示色号、符号、名称、数量、平均色差和待确认格数。

## 为什么使用原生 Canvas

拼豆图纸是规则、密集、可批量绘制的二维网格。Canvas 2D 可以在一次绘制中完成背景、网格、豆体和符号，并避免为每颗豆创建 DOM 或场景图对象。当前交互需求只有命中测试、缩放、画笔、橡皮和填充，原生 Canvas 足够且依赖更少。

如果未来加入任意旋转对象、复杂选区变换、协同标注或大量非网格矢量对象，再评估 Konva；只有在超大场景持续动画或 GPU 着色器成为明确瓶颈时才评估 PixiJS。

## 色号准确性的边界

- 屏幕上的 RGB/HEX 只用于预览，不能替代品牌、系列、色号和实物测色数据。
- 量化算法只能在给定色卡中寻找最接近颜色，无法修复不准确或不完整的色卡。
- 正式品牌色卡应记录来源、版本、测量条件和许可状态，并保留旧版本以重现历史项目。
- 平均色差用于总体质量提示；低置信度格表示最优与次优候选过近，应该允许人工复核。

## 性能与失败策略

- OpenCV 位于独立 Worker chunk，只有用户点击转换时才加载。
- 图像颜色会汇总为最多 4,096 个带权颜色桶，并在 Worker 内完成色卡量化，避免大图阻塞界面或产生无界距离矩阵。
- Worker 转移像素缓冲区，避免复制大数组和阻塞 Vue 响应式状态。
- OpenCV 初始化或处理失败会自动退回 Canvas 路径，不让用户丢失本次导入。
- 项目文档采用版本号和运行时校验，损坏或尺寸不一致的数据不会写入编辑器状态。
